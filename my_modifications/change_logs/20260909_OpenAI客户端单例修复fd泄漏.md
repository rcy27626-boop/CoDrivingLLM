# 20260909 OpenAI 客户端单例化：修复 fd 泄漏导致的 Too many open files

## 一、问题现象
- 长时间运行（跨 2 个 episode、累计数百~上千次 LLM 调用）后崩溃：
  - 中间：`APIConnectionError: Connection error.`
  - 底层：`httpcore.ConnectError: [Errno 16] Device or resource busy`
  - 收尾：`OSError: [Errno 24] Too many open files: '...progress.json'`
- 复现规律：修改前 32b 跑 845 次调用可跑完（低于 ulimit 1024）；修改后无论 27b 还是 32b，调用总量跨过约 1024 后必然崩溃。与模型无关，与运行总调用量有关。

## 二、根因
- `llm_controller/llm_agent_action.py` 与 `llm_controller/llm_agent_negotiation_system.py` 的
  `send_to_chatgpt()` 每次 LLM 调用都执行 `client = OpenAI(...)`，且从不 `client.close()`。
- 每个 OpenAI 客户端 = 一个 httpx 连接池 + 常驻 keep-alive socket；全库 4 处 `OpenAI(` 实例化、0 处 `.close()`。
- 进程文件描述符（fd）被逐步耗尽后：无法新建 socket 连 ollama（ConnectError），也无法打开结果文件（Too many open files）。
- `memory.py` 的嵌入客户端同理（每个 DrivingMemory 新建一个，仅 few-shot/建库路径会触发）。

## 三、修改内容
1. `llm_controller/llm_agent_action.py`
   - 新增模块级惰性单例 `_llm_client` + `_get_llm_client()`，进程内只创建一次；
   - `send_to_chatgpt()` 改为复用 `_get_llm_client()`；
   - 客户端参数：`timeout=1800.0`（本地大模型单次生成可能较慢），`max_retries=1`（减少重试建连）。
2. `llm_controller/llm_agent_negotiation_system.py`
   - 同样新增模块级单例并复用。
3. `llm_controller/memory.py`
   - 新增 `_embedding_client` 单例 + `_get_embedding_client()`，`SiliconFlowEmbeddings` 改用它。

## 四、验证
- `python -m compileall` 通过。
- Mock OpenAI 单测：action/negotiation 各仅实例化 1 次、多次调用返回同一对象；
  memory 嵌入客户端同样单例；timeout/max_retries 参数正确传入。

## 五、服务器待验证命令
```bash
# 1) 先确认默认 fd 上限
ulimit -n

# 2) 运行期间另开终端观察 fd 数量是否稳定（替换为实际 PID）
watch -n 5 'ls /proc/<PID>/fd | wc -l'

# 3) 用 --no-video 长跑 2 个 episode 验证不再崩溃
python Run_multi_CAV_LLM.py --scene intersection --method 0shot --n 2 --seed 42 --no-video --batch fd_fix_verify
```

## 六、影响范围
- 仅重构客户端创建方式为进程级复用，不改任何 prompt/消息/逻辑；
- 顺带减少每次请求新建 TCP 连接的开销（预期单次调用耗时略降）。
- 需用户确认后提交推送，服务器 pull 后生效。
